# DSH 通用长任务插件

当前版本：`0.1.2-rc.19`（发布候选版）。安装、运行协议及尚待验证的流程以 [RELEASE.md](RELEASE.md) 为准。下文 rc.14–rc.18 标题记录功能引入版本，均包含在当前版本中。

rc.19修复：补齐中英文执行/浏览器要求的识别，文档说明、引用示例和否定句仍按语境判断；`review`不能取消识别出的实测要求。业务模块`dependsOn`按当前批次的交付文件映射到前置批次，全部前置完成并核对产物版本后才接续；兼容`assignments.waitFor`，两类条件须同时满足。检查点持久化，恢复不跳过未完成依赖，投递未知保持暂停。模块图与批次顺序/交接互锁会在确认前拒绝；同一批内模块作为原子组处理，需要强制先后的模块应拆批。归档rc.18的验证记录保留；rc.19安装核对与完整桌面任务验收分别记录。

## 原任务补测与报告附件（rc.18）

`longtask_control` 的 `verify` 可同时传入 `expectedVersion`、原标准 ID 的 `criteria` 修订、`verificationPlan`、`verificationScope: {included, excluded}` 和原因。用户确认时会看到前后差异；确认后沿用原任务、产物和预算，只重开独立验收。新增开发要求走 `reopen`，也可在同一次修订提交计划与范围。

已有系统复验提案使用 `workKind: "verification"`，可以只交报告，引用既有测试脚本作为检查输入；仍需每条标准有人负责、交付文件唯一归属和独立验收。开发任务保留模块与源码分工规则，纯文档继续按其实际标准验收。

每轮交付在数据目录 `acceptance-reports/<taskId>/v<version>/<roundId>/` 单独导出最终签署报告、证据 JSON、检查计划和 `reproduce.mjs`。`longtask_tasks` 的 `finalAcceptanceEvidence` 返回路径、导出状态和错误。写入失败保留待处理快照，重启时重试；附件不改已冻结报告。历史导出明确区分历史签署与新增实测。

```powershell
node scripts/export-acceptance.mjs --state <state.json绝对路径> --out <独立输出目录> --task <taskId>
node <附件目录>/reproduce.mjs --workspace <项目目录>
node scripts/crm-verification.mjs --workspace <crm-leads目录> --mode all
```

历史导出只读源状态。复现与示例在临时副本执行，手动复现不能代替宿主沙箱中的正式独立验收。CRM 示例覆盖接口测试、HTTP 资源、从 README 表格读取账号并核对登录身份；不覆盖浏览器渲染/交互或全新依赖安装。正式计划若新增项目检查脚本，应将脚本纳入项目输入和交付分工，再由独立验收调用 `longtask_verify`。

## 实测验收（rc.16）

rc.17 区分文档内容与实际执行：例如“文档说明 npm test 和浏览器兼容性”可按 review 静态核对；“按文档实际运行 npm test 并通过”仍需 command，“实际用浏览器登录并验证刷新会话”仍需 browser。同条标准中“编写说明，并实际运行”的两个要求分别保留。纯文档写作不因为涉及 API、数据库、测试等技术主题就要求开发模块分工。用户明确声明的 command/browser 会保留，不被文档语境自动取消。

新软件方案为每条 `criteria` 明确 `verification: ["review"]`、`["command"]`、`["browser"]` 或多种方式。review 适用于文档、结构和代码审查；要求测试通过、服务启动、接口行为或浏览器操作的标准须实测，不能靠阅读代码判通过。明确的运行/浏览器条文会与声明方式合并，不能用 review 降级。

实测标准在 `verificationPlan` 中关联检查。例如（项目路径换为任务工作目录内实际项目）：

```json
{
  "workspace": "C:/projects/crm-leads",
  "checks": [
    {"id":"api","kind":"command","criterionIds":["C1"],"purpose":"运行接口集成测试并断言退出码与行为","program":"node","args":["scripts/verify-api.mjs"],"timeoutMs":120000},
    {"id":"ui","kind":"browser","criterionIds":["C2"],"purpose":"浏览器登录、增删改查、刷新会话并核对控制台","program":"node","args":["scripts/verify-browser.mjs"],"timeoutMs":120000}
  ]
}
```

检查脚本、测试用例与依赖声明应列入交付文件，由分工中的测试负责人实现；该职责可兼任，不要求固定增加一位专家。独立验收人先审查脚本是否实际断言目标行为，再调用 `longtask_verify({checkId})`。命令型检查须真实运行测试/服务验证；browser 脚本须实际使用浏览器自动化并检查预期交互、页面及控制台，不能打印一句成功替代。项目必须具备对应依赖和浏览器环境；本插件提供受控脚本执行，不内置或自动下载浏览器。

专用工具复制项目（含项目内依赖）到独立临时目录，忽略 `.git`、`.longtask`、`.env*`，拒绝指向项目外的依赖链接。固定 program/args 通过宿主沙箱 shell 以副本为写入根运行，原目录不接受安装或修改。脚本可在副本中创建临时数据库、运行服务、测试及截图，并应自行收敛后台进程；每项检查有明确超时。Linux/macOS 下原项目不能位于宿主沙箱默认可写临时区域。Windows 使用宿主 ACL 沙箱，继承其 partial enforcement 边界；副本按文件复制，不建立源文件硬链接。

每项检查在各自的新副本内运行，不能依赖前一检查留在临时目录中的状态。若需准备依赖、启动服务再测试，应在同一检查脚本中完成；依赖不得依靠项目外符号链接。缺沙箱服务、读取环境或浏览器能力时明确报告能力缺口，不降级为无沙箱执行。

工具生成真实运行 ID，记录任务/标准版本/轮次/epoch/验收身份、检查、冻结产物、测试与依赖输入摘要、退出码和输出日志。验收结论在 `verificationRunIds` 引用对应记录；交付前复查记录、日志与当前输入版本。失败、超时、无沙箱证据、过期/伪造 ID 或缺少任一已关联检查均不能通过，任务保持待实测。运行记录证明已执行对应检查，不能代替独立验收人对测试质量与覆盖面的审查。

已交付或 `paused/missing_input` 的历史任务，可用 `longtask_control` 的 `action:"verify"`、`expectedVersion`、`verificationPlan` 经用户确认补测；只升标准版本、重开独立验收，沿用产物与已用费用，不重跑开发、不追加预算。`longtask_tasks` 返回 `runtimeVerification`，历史 delivered 缺少实测时会明确列出缺口，不自动改写旧状态。

恢复确认依赖宿主审批。当前会话为 `never` 时应由用户切换为允许审批的模式后再操作；插件不会自动修改策略或绕过拒绝。运行信息应包含 `userEntryProtocol=7`、`verificationEvidenceProtocol=1`。

核心插件独立提供长任务操作入口。用户在普通DSH对话中提出要求，当前Agent通过以下正式工具操作同一任务内核。

## 用户怎样操作

例如：

> 把比较两种存储方案作为长任务，交付比较表和推荐结论。先给我方案和专家分工，开工前让我填写人民币预算。

DSH检索专家、提出目标/完成标准/产物路径/分工/独立验收人，可建议预算金额。用户可调整待确认方案。确认工具通过宿主userQuestions展示完整方案并要求用户填写人民币总上限（例如5或2.50）；提交金额即确认开工。建议金额不自动生效，未填写或关闭面板均不开工。

运行中可直接说：

- “列出我的长任务。”
- “查看任务 task_… 的状态、成果和用量。”
- “暂停任务 task_…。”
- “恢复任务 task_…，沿用原预算。”
- “取消任务 task_…。”

恢复也需宿主确认；预算不足或答复投递结果未知时继续保持暂停。不会自动加额或把unknown当成未投递重发。模糊目标应先在对话中澄清；本插件不另开一个Router模型。

也可回答任务澄清、补充信息、确认纠错重开或更换执行专家；新增要求用关联待确认任务单独计预算。完整安装、升级、回退和发布验收步骤见[RELEASE.md](RELEASE.md)。当前`0.1.2-rc.19`包含职责与业务模块分工、角色简报、顺序批次、受控实测、同任务补测修订和最终验收附件；默认跟随DSH最终请求输出上限。离线回归、安装启动核对与完整桌面任务验收分别记录，不能互相替代。

Worker 等待工具审批时，主会话会收到待办摘要，包括 Worker 会话编号、工具、原因和审批编号；任务查询也会列出全部待审批项。请打开对应 Worker 的 DSH 审批卡片批准或拒绝，Router 中发送“继续”不构成授权。决定后由宿主继续原工具调用，插件只更新等待与通知，不额外催跑。取消、撤权或轮次结束会使等待失效；运行时重载后原审批不能重放，相关任务暂停供用户核对。

## 正式工具

`longtask_experts` 支持 `query`（中英文关键词）、`task`（完整目标与技术栈）、`offset`、`limit`。例如：

```json
{"task":"开发Vue3与FastAPI客资系统，SQLite持久化、接口鉴权、pytest回归","query":"数据库","limit":5}
```

结果中的目录页由 query 过滤和分页，职责推荐则基于完整 task 与全目录产生；数据库、测试、安全等候选不会被前端/后端目录页遮住。每个职责最多给出两位实际存在的候选，简介截短，不将专家正文放入Router上下文。软件任务区分执行职责和独立验收，非开发任务不强加这套分工。

提案和任务查询返回 `staffingReview`，确认面板会提示哪些执行方向尚未选择专职专家。小任务可由现有人选兼任；这些是规则和元数据生成的初步提示，不是能力证明或强制扩编。Router应核对候选适配性，说明谁负责兼任、如何验证，再由用户确认人数和预算。新发现专家不会自动加入已有任务。

rc.7对新软件方案增加开工前校验。`executionPlanValidation.errors`必须为空才可确认；`assignments`必须逐项填写：

- `module`：本人负责的模块名称。
- `responsibilities`：推荐结果中的执行职责ID；同类职责可由不同业务模块的专家承担。兼任多项时填写`coverageRationale`说明落实办法。
- `criterionIds`：分配给该工作分工的完成标准编号，跨模块端到端标准可由多位专家共同引用。
- `deliverables`：总清单中本人负责的确切绝对文件路径，含实现/测试源码，不能仅列README。总清单最多128项。
- `batches[{id,title,deliverables}]`：1..32个顺序批次，每批1..4文件，批次文件须覆盖本模块全部交付文件且不重复编排。

例如，一个模块的批次为`骨架 → 数据模型 → 接口 → 回归`。执行者只收到自己的标准、当前批次和批次路线。完成时使用`<longtask_report>{"done":true,"batchId":"当前批次ID","next":[],"waiting":null}</longtask_report>`。`done=true`表示本批完成；文件齐备性通过后才推进下一批，所有模块批次完成才进入独立验收。该检查不能代替功能测试和独立验收。

任务查询返回`batchProgress`。暂停/重启后按已保存批次继续；验收缺项交回标准所属模块。`reopen`可同时提供新的`assignments`，用于明确新增标准的归属，不改变已批准总金额。非软件任务可显式提供批次计划使用该机制；已开工旧任务继续原协议，不自动改组或迁移。

默认`workerMaxTokens: "host"`，不在Worker的AgentOptions中设置固定输出上限，也不裁小DSH请求钩子返回的值。DSH补齐模型默认值并绑定供应商后，插件在最终流发出前读取实际`maxTokens`，按“输入上界＋实际输出上限”预留Token，并用同一上限及实际路由预留金额。每次重试重新核对；缺少有效上限或预算不足则暂停，供应商不会收到该次请求。派工/开步时上限尚未知，只核对最低输入条件，不能视为完整请求已准入。

rc.8修正宿主与插件使用不同SDK副本时的兼容性：以真实会话和单次请求准备匹配，不依赖SDK内部WeakSet标记或取消信号的对象引用相等。当前任务授权、两侧取消状态和足额预算仍会核对。

rc.9修正Watchdog误判：恢复/重启执行时重新计算观察窗口；成功写入当前交付文件且内容变化就记录进展，不必等整个批次结束。失败、重放或反复写相同内容不刷新计时。已经取消而缺少用量的请求仍须对账，升级不会把它当成零费用。

rc.10增加Router可见通知卡片：宿主Chat会隐藏普通上下文注入，仅写入form=notice不足以显示。客户端按本插件消息来源建立独立可见行，旧通知也能展示；卡片可打开对应Worker，批准/拒绝仍在DSH原生审批卡片处理，不会为提醒本身启动模型。通知协议为routerNoticeProtocol=3。

rc.11补齐Router职责：会话绑定已确认、未结束的托管任务时，主会话负责查询、沟通与正式调度，代码写入、shell执行和独立子Agent委派交给已登记Worker。暂停任务需通过正式入口恢复；“开发完成了吗？”仅是进度查询。普通会话和未确认提案不受此职责约束，任务取消或交付后解除。用户要改为主会话直接执行时，先正式取消托管任务以保留费用及产物记录。

rc.12修复已完成模块收到留言而误暂停全任务：普通交接保留记录，完成的模块不再启动；无未结算请求的完成模块blocked只保持等待，其他模块照常执行。未完成执行者的真实准入拒绝仍需要在主会话核对原因。

rc.13取消Worker默认累计24步硬停：`executorMaxSteps: 0`表示按真实预算和实质进展继续，不再跨批次累计到第25步就停；正整数配置仍可选择固定上限。验收步数策略保留，不自动增加预算或恢复任务。rc.13同时包含rc.12修复。

已有配置若显式填写正整数，仍沿用旧版限额模式；要启用跟随模式请改为`"host"`并完整重启。每批文件数和大文件分段指令保留；DSH及供应商自身的输出上限、截断提示和有限次接续仍然存在。普通DSH会话的请求和费用不受Worker预算钩子影响。

| 工具 | 用途 |
| --- | --- |
| longtask_experts | 检索本地专家简介和稳定相对路径 |
| longtask_propose | 提出方案，或调整从未执行的待确认方案；不派工 |
| longtask_confirm | 展示指定版本的方案并请求宿主用户确认；同意后开工 |
| longtask_control | 暂停/恢复/取消、答复澄清、补充/澄清、纠错重开、替换执行专家；不自动加额 |
| longtask_tasks | 分页列表，或指定taskId查看方案、状态、预算、产物引用和验收进度 |

`longtask_propose`必须明确`goal`、`criteria[{id,text}]`、绝对路径`deliverables`、`executorRelPaths`、`acceptorRelPath`；可传`suggestedBudgetCny`（十进制字符串，仅建议），不再接受`budgetTokens`或模型代填的金额上限。多专家方案还需`assignments`。验收人必须独立。修改待确认方案时带`taskId`和`expectedVersion`；确认时带当前`taskId`和`version`。

新增要求提供`parentTaskId`，生成关联proposed任务。`longtask_control`的`answer/supplement/clarify`提供`text`；`reopen`提供`criteria`和`expectedVersion`；`replace_executor`提供`addRelPath/removeRelPath/expectedVersion`，可附`pendingItems`。答复恢复、纠错重开与换人均先走宿主确认，拒绝时不变更任务；未知用量和未知投递不能通过这些入口绕过。

执行者、验收者及其后代不能调用这些管理工具。真实宿主创建Worker时会从其工具面隐藏这些入口；正文和单调guard同时校验任务身份。任务内专家通信仍使用原有协议。

## 宿主与配置

需要DSH的agents、sessions、tools服务，新任务开工所需的userQuestions.ask输入通道，以及恢复等动作所需的approval.request确认通道。缺通道时保持原状态，不降级成自动开工。SDK参照0.2.1-rc.5，并已使用桌面实际携带的0.2.2-rc.1完成同套回归。

安装核心bundle后，在当前profile配置：

- `dataDir`：正式任务状态与日志目录。
- `agencyAgentsRoot`：本地专家定义库，含divisions.json。
- `workerCwd`：存在的绝对任务工作目录，正式使用时设置到目标工作区。
- `workerProvider`、`workerModel`、`workerMaxTokens`、`workerPreset`：宿主可用模型和能力集。
- `acceptorReadOnly`：正式bundle显式启用；一般工具限于读取/检索及明确配置的受控核对工具，任意写入和shell被拒绝。独立验收可用专用`longtask_verify`在沙箱副本执行已确认检查；不依赖另装preset。旧profile默认兼容旧行为，可显式启用。
- `acceptorPreset`：可选验收能力集；启用只读白名单后仍受其约束。
- `modelPrices`：按精确provider/model配置人民币价格；数组覆盖内置表。金额与单价均为十进制字符串，单位为元/百万Token，详见配置示例。缺价、过期或币种不支持时拒绝金额请求。

任务入口会显示当前工作目录；交付路径必须为绝对路径。工具权限与沙箱仍由DSH宿主管理，不会因插件生成方案而扩大权限。

提案前普通DSH对话的模型费用由该宿主会话显示；正式工具本身不发模型请求。已确认任务的账本覆盖托管执行、验收、返工及监督等请求；本入口不接管用户主会话的全部消费。

## 金额预算的口径

用户只需设人民币上限。请求前按输入估算和最大输出预留金额，所有专家共用同一事务账本；响应后依据SDK返回的互斥用量分项和本次请求价格快照核算。失败重试单独计费，重复事件不重复记账；费用未知保留预留并暂停。金额内部以纳元整数持久化，不逐次舍入到分。

内置价格仅支持`deepseek-official/deepseek-flash`，来源为[DeepSeek官方价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)。2026-11-06核对的高峰价为：缓存输入0.04、未缓存输入2、输出8元/百万Token；缓存写入按未缓存输入保守核算。为避免峰谷边界和节假日误判，首版统一按高峰价核算，价格有效期至2026-12-06北京时间0时。**核算费用不是平台实扣**，空闲时段实际费用可能更低；价格过期需要更新配置，不静默沿用。

预算包含本任务托管模型请求，不包含用户主会话或第三方付费工具；账户余额差不用于给任务归属费用。保留收尾、验收和其他专家报告额度，并按金额压力提前收尾。单次输出截断有已结算用量且原预算允许时接续原Worker；连续截断最多自动接续两次，仍无进展则暂停。

历史Token任务保持原账本和原上限，不自动折算人民币；切换预算单位需新建任务。首轮输入仍依赖声明基线，宿主隐藏的动态系统提示和工具定义不完全可见，因此本插件不是供应商侧的绝对消费硬限额。

## 主会话状态反馈

任务由正式入口的实际调用方会话绑定Router，不由模型填写会话ID。后台发生自动暂停、单次输出截断接续、独立验收交付时，只把任务ID、状态、原因及预算摘要写到这个主会话。使用DSH的notice来源元数据，折叠行也有状态摘要；展开可查看原因和操作提示。不转发专家定义、原始讨论或产物全文。

这些记录不会调用followup/steer，也不为了播报再请求模型；Router下一次正常交互可读取。主会话未加载时持久保留待投递，不借其他会话广播；恢复加载后核对稳定消息ID，避免重复显示。过期暂停状态不在任务恢复后误投。

宿主Worker中的“发送继续”是通用截断提示，不能解除插件任务暂停。单次输出截断满足条件时插件会自动接续；已暂停时应在主会话说“查看任务 task_… 的暂停原因”，处理后再说“恢复任务 task_…，沿用原预算”。金额不足或费用待核对不能靠继续绕过。旧任务没有Router绑定时不猜测收件人，用户从主会话批准恢复等操作后绑定该主会话。


## rc.14 限制与恢复规则

职责覆盖允许多位专家按业务模块承担相同能力，完成标准允许多个模块共同引用；每个交付文件仍有唯一负责人。共享标准返工会通知所有参与模块，专家按自己的文件和批次执行。源码识别不限定于固定语言后缀。

默认不设置固定读取次数。`toolReadBudget`为正数时只给超阈值Worker一次定向提醒，不禁止必要阅读、源码核对或测试。截断只对连续无实际进展的接续计数，真实产物推进会重置；用户显式恢复也开启新窗口。

验收按轮次计步，同轮普通重启沿用检查点；用户显式恢复保留核对摘要并新建验收会话，旧会话撤权。输出截断在原预算和本轮步数内继续，真实错误明确暂停。已登记宿主命令有`backgroundJobTimeoutMs`等待窗口（默认两小时），重复登记不会延长；超时仍进行纠偏。

验收保护按输入与输出各自价格计算，首轮产物读取按`acceptanceReadBudgetBytes`规划（默认64KiB，可用分页/索引/抽样），避免文件越大就强制假设全文进入上下文。这是未来收尾规划；每次实际模型请求仍按真实输入上界、DSH最终输出上限及当前金额余额硬准入。

验收的一般工具默认限于文件读取/检索；rc.16起另有专用`longtask_verify`执行已确认的沙箱检查。宿主如已提供只读联网、预览或隔离验证工具，可将确切工具名加入`acceptorReadTools`；此配置不安装新工具，不支持任意shell、写入或模型委派。方案可声明`acceptorRequiredTools`，确认前检查只读政策，验收开步前在实际Agent作用域检查工具，兼容preset提供的会话工具。不能核对时，验收输出`outcome: "gap", gapKind: "capability"`及所缺能力，任务保留当前验收轮次暂停，补齐能力后恢复，不反复返工正确产物。


### 先拆业务模块，再选专家

rc.14的新软件提案使用`executionPlanVersion: 2`，需要`workModules`业务责任矩阵。每项包括`id/title/scope/leadRelPath/criterionIds/deliverables`，可含`contributors/dependsOn`。例如客资系统按线索采集与去重、客户与跟进、分配规则、权限审计和报表拆解，再为这些业务模块选择界面、服务、数据和测试专家。`assignments`仍描述各专家的技术职责、唯一归属文件与执行批次。

插件检查业务标准与交付物是否覆盖、参与者是否有对应实际分工、依赖是否成环，拒绝仅把“前端/后端”当全部业务模块的方案。三个及以上业务模块只选一至两位专家时，必须提供`staffingRationale`说明合并理由、逐批安排与测试职责，并展示工作量提醒。合理的小团队可以通过，插件不以固定专家人数代替分工质量。确认视图、角色简报、验收、换人和重开均保留该矩阵。

已确认的旧版任务保持原分工和协议，不因升级自动增派专家、改预算或重新开工。


## rc.15 验收读取与进展

验收工具白名单使用实际Agent作用域，保留预设继承的read/glob/grep；不能用省略scope的全局查询构造名单。首次请求默认检查read能力，缺失时在`acceptorToolWaitMs`内等待，期间不发模型请求。模型组装快照已经生成后工具才就绪时，旧帧在计步/预留前退出，保留同轮检查点并新建验收会话重组；自动重建后仍缺能力则明确暂停，不无限重试。

`acceptorMaxSteps`默认0，不再固定8步暂停。`acceptorProgressWindowSteps`默认8，表示检查点间隔；新的成功产物读取或受控核对证据支持继续，仍受原金额和实际请求上限约束。`acceptorMaxIdleSteps`默认3：先纠偏，经过同等窗口仍无进展才暂停。仅切目录、失败调用或重复读取同一片段不算进展；相对路径按宿主实际工作目录解析，图片/附件结果也可作为去重核对证据。显式配置正数acceptorMaxSteps仍提供固定硬上限。
